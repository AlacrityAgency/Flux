# بازبینی حافظهٔ تولیدشده از NotebookLM

منبع منتخب و تنها source در metadata ارجاع‌ها: `66864cc3-7f85-48da-aaf6-5f35c4809b19`. یادداشت دارای ۵۱ ارجاع بومی: `f2d69424-87cd-4e79-81ae-a5c32ff069eb`، در [دفتر پروژه](https://notebooklm.google.com/notebook/cbd54447-058f-445c-a1e3-850f15cc5eb9).

پاسخ خام انگلیسی در `head-memory-v0.5-notebooklm.md` و metadata ارجاع‌ها در JSON هم‌نام حفظ شده‌اند. پاسخ فارسی اولیه با note ID برابر `08cca1f8-cc08-45f6-82f6-d486c2c8bde6` شماره‌های ارجاعی دارد که metadata آن‌ها را نگاشت نکرد؛ از آن به عنوان ارجاع ماشینی معتبر استفاده نمی‌شود.

حافظهٔ قابل استفادهٔ HEAD، نسخهٔ فارسی `head-memory-v0.5.fa.md` است. متن خام RAG مستقیماً وارد حافظهٔ تأییدشدهٔ برنامه نشده است. این تفاوت‌ها پس از تطبیق با سورس تصحیح شدند:

1. جملهٔ عمومی «PASS به execution evidence نیاز دارد» در پاسخ خام بیش از اندازه سخت‌گیرانه است. هر معیار نوع شاهد خودش را دارد؛ معیار `source_document` می‌تواند با شاهد معتبر همان نوع PASS شود. فقط معیار اجرای آزمون به `test_execution` موفق وابسته است. شاهد تعریف آزمون، شاهد اجرا نیست.
2. هنگام اجرای فعال، تغییر حافظهٔ مؤثر رد می‌شود؛ epoch نشست‌های بومی مربوط را برای نوبت بعد تازه می‌کند. تاریخچهٔ قابل مشاهده و متن قبلاً فرستاده‌شده به سرویس خارجی پاک نمی‌شوند. «پاک‌سازی active conversation» نباید به حذف تاریخچه یا لغو خودکار همهٔ اجراها تعبیر شود.
3. assessment واژگانی خود بسته همچنان `semantic_sufficiency=unverified` دارد؛ بازبین در گیت مستقل نتیجهٔ معیار را تعیین می‌کند. بازبینی این فیلد بسته را خودکار به verified تبدیل نمی‌کند.
4. پیشنهاد نهایی مدل دربارهٔ مرحلهٔ بعد، درخواست صاحب پروژه یا مجوز اجرای آن مرحله محسوب نمی‌شود؛ از حافظهٔ عملیاتی حذف شده است.

بررسی اضافه پس از snapshot NotebookLM: خود EXE نصب‌شده با Gemini API و DB موقت پاسخ واقعی `FLUX_PACKAGED_GEMINI_OK` داد. گزارش `packaged-gemini-live-check.json` با hash همان EXE، یک درخواست فیزیکی و مصرف گزارش‌شدهٔ ۱۰۴ ورودی/۱۱ خروجی ثبت شده است. این بررسی علاوه بر چهار درخواست اولیهٔ API است؛ مجموع درخواست‌های تولید مستقیم Gemini API در این کار پنج است، سه ناموفق و دو موفق. مبلغ صورتحساب واقعی تأیید نشده است.
