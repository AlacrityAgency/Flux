# FLux v1 — Codex + GapCode

این اسکیل گردش‌کار «مدل اقتصادی → بررسی مستقل → ارتقا» را اجرا می‌کند. Laya محلی ابتدا و پایان هر تلاش تصمیم می‌دهد؛ صحت از شواهد و تست مستقل می‌آید. این فایل دستور اجرای عامل است، نه سرویس پس‌زمینه یا مسیریاب خودکار نصب‌شده در Flux.

## شروع و منابع

- برای تعریف دقیق قرارداد، برنامهٔ ارتقا و مرز اندازه‌گیری، [algorithm.fa.md](references/algorithm.fa.md) را بخوان.
- برای اتصال، مدل و effort، فقط [models.json](references/models.json) و نتیجهٔ تاریخ‌دار [model-tests.fa.md](references/model-tests.fa.md) را مبنا قرار بده. نام مدل را از روی خانواده یا نام در MCP GapGPT حدس نزن.
- helper اصلی [call_model.py](scripts/call_model.py) از CLI واقعی Codex یا GapCode، ورود ذخیره‌شدهٔ همان CLI، sandbox خواندنی و جلسهٔ مستقل استفاده می‌کند. کلید یا cookie درخواست نکن، فایل auth را نخوان و تنظیم عمومی کاربر را تغییر نده.
- [laya_decision.py](scripts/laya_decision.py) به interpreter دارای Laya/Torch و checkpoint محلی نیاز دارد. آن را یک بار در یک فرایند بارگذاری و برای تمام تصمیم‌ها نگه دار. اگر Laya موجود نیست، صریحاً بگو اجرای فاقد Laya است؛ تصمیم یک LLM را به نام Laya ثبت نکن.

## قرارداد و آماده‌سازی

قبل از فراخوانی، درخواست، خروجی مطلوب، قیدهای اجباری، نوع مسئله، facts، ریسک، معیار مستقل موفقیت و بودجهٔ تلاش را مشخص کن. خانوادهٔ مسئله به‌تنهایی اثبات پوشش قیدهای متن نیست. برای درخواست مبهم، بخش قابل‌انجام را پیش ببر و فقط اطلاعات ضروریِ واقعاً نامعلوم را بپرس.

داده‌ها را یک بار در facts نگه دار. قید را برای کوتاه‌کردن prompt حذف نکن. در حالت پروژه‌محور، فقط شواهد ضروری از پروژهٔ درست و revision درست را اضافه کن؛ کاهش RAG در آزمون این اسکیل سنجیده نشده است.

برای فاکتور، شمارش محدود و زمان‌بندی با قرارداد شناخته‌شده، خروجی مورد انتظار:

```json
{"refs":["تمام کلیدهای سطح اول facts"],"code":"def solve(facts): ...\ndef check(answer, facts): ..."}
```

refs فقط کلیدهای سطح اول facts است؛ مثلاً برای فاکتور `["lines","shipping","tax_percent"]`، نه qty و unit_cents داخل lines. solve داده را از facts می‌خواند؛ check از answer و facts با محاسبه‌ای مستقل استفاده می‌کند. از literal دادهٔ تکراری، گراف تولیدی و توضیح طولانی پرهیز کن. برای وظایف دیگر، پاسخ مستقیم/تابع/patch با قرارداد و تست مناسب انتخاب کن؛ همهٔ وظایف را به solver عدد صحیح تبدیل نکن.

## انتخاب مدل و provider

برنامهٔ پیش‌فرض mixed برای قرارداد compact:

| فرصت | provider/model | effort |
|---|---|---|
| ۱ | codex/gpt-6-luna | low |
| ۲ | gapcode/gpt-6.1-sol | high |
| ۳ | gapcode/gpt-6-astra | high |

انتخاب صریح کاربر برای provider/model مقدم است. پروفایل codex-only یا gapcode-preferred را مطابق مرجع و قابلیت‌های ثبت‌شده تنظیم کن. GapCode Luna در ping کار کرد، اما نمونهٔ compact آن refs غلط داشت؛ فعلاً در پیش‌فرض compact فعال نیست. Fable در compact موفق بود و می‌تواند با انتخاب صریح/برنامهٔ پیکربندی‌شده استفاده شود. قیمت کیف پول GapCode نامعلوم است؛ «ارزان‌ترین مدل جهان» یا ترتیب قیمت تمام خانواده‌ها را ادعا نکن.

فقط endpoint فعال را فراخوانی کن؛ برای compact، `compact_qualified=true` لازم است. effort را از supported_efforts انتخاب کن؛ high ثبت‌شده در کاتالوگ الزاماً live-tested نیست. مدل‌های native-blocked، 402، timeout یا ناسازگار با قرارداد تا retest موفق در همان محیط، در آن حالت فعال نمی‌شوند. گزارش درخواست سمت client را گواهی مستقل هویت مدل سمت server ندان.

## Laya ابتدا و بررسی

FRONT در نسخهٔ اسکیل فقط عمق بررسی light/medium/full را انتخاب می‌کند؛ مدل و effort از برنامهٔ Senior می‌آیند. پرسش‌های پیشنهاد مدل/effort که در benchmark قبلی پرسیده می‌شدند و Senior آنها را اعمال نمی‌کرد، اینجا حذف شده‌اند. این تغییر در تست اتصال اسکیل اجرا شده، اما benchmark کاهش هزینهٔ تازه‌ای برای آن نداریم.

کف بررسی را از ریسک تعیین کن: low حداقل light، medium حداقل medium، high همیشه full. قید اجباری، تکمیل provider و سازگاری schema در همهٔ سطوح لازم است. probabilities گزینه‌های Laya، احتمال کالیبره‌شدهٔ صحت مدل نیستند.

## فراخوانی و بررسی پاسخ

از helper، prompt-file و receipt تازه استفاده کن. اجرای غیرهمانند را در رسید قبلی ننویس و پاسخ ذخیره‌شده را آزمایش تازه ننام. سقف پیش‌فرض timeout هر wire call برابر ۹۰ ثانیه است و می‌تواند پیش از اجرا در برنامه تغییر کند.

پاسخ فقط با `turn.completed` و exit=0 کامل است. خروجی بدون رویداد تکمیل، usage نامعلوم، timeout و خطای اتصال را ثبت کن. ابزار مشاهده‌شده در حالت solver مستقل باعث رد پاسخ می‌شود.

برای compact، تنها JSON خالص یا یک حصار کامل JSON بدون متن اضافی را با `normalize()` باز کن. کلید تکراری، JSON چندتکه، NaN و توضیح آزاد رد می‌شوند. این normalization مشخصاً برای سازگاری Fable افزوده شده؛ استخراج حدسی JSON از متن انجام نده.

[validate_program.py](scripts/validate_program.py) refs، امضا، AST، worker و checker را بررسی می‌کند. worker در subprocess با timeout پنج ثانیه اجرا می‌شود؛ کد باید مجموع solve/check را در چهار ثانیه تمام کند. سپس ارزیاب مستقل مسئله را بیرون از برنامهٔ تولیدی اجرا کن. `independent_verifier_pass=null` از helper یعنی هنوز این مرحله انجام نشده، نه موفقیت.

برای پاسخ عدد صحیح از worker بسته‌بندی‌شده استفاده کن. برای خروجی اعشاری/نوع ناشناخته، قرارداد و runner مناسب جدا لازم است. worker محدود به builtin/importهای مشخص است؛ bin و type، IO، introspection و نام‌های خصوصی در دسترس نیستند. این worker sandbox کامل سیستم‌عامل یا حد سخت RAM نیست؛ برای کد ناشناسِ نامطمئن کافی نیست.

## Laya پایان و ارتقا

END فقط درخواست عمومی، candidate، تکمیل provider، نتیجهٔ بررسی و فرصت‌های باقی‌مانده را می‌بیند. پاسخ مرجع و کد oracle وارد prompt حل‌کننده یا Laya نشوند.

```text
اگر بررسی شکست خورد:
    فرصت مانده → ارتقا؛ فرصت تمام → توقف با شکست
اگر بررسی پاس شد و Laya درخواست ارتقا داد و فرصت مانده:
    ارتقا
در غیر این صورت:
    قبول بر اساس شواهد بررسی‌شده
```

`guard()` را اعمال کن؛ confidence یا accept خام نمی‌تواند بررسی ناموفق را دور بزند. حداکثر سه wire call در کل درخواست، شامل خطاهای provider. هر ارتقای کیفی، مدلِ مرحلهٔ بعد و high/full می‌گیرد. شرح خطا حداکثر ۲۴۰ کاراکتر؛ کل پاسخ/گراف قبلی دوباره ارسال نشود. facts و قیدها ثابت بمانند.

برای خطای اتصال، provider دیگرِ همان مدل را اگر فعال و فرصتی باقی است امتحان کن؛ این کار را ارتقای هوش مدل ننام. 402 را بدون تغییر اعتبار retry نکن. timeout ممکن است مصرف نامعلوم داشته باشد؛ بدون ثبت شکست دوباره نفرست. retry داخلی CLI و تعداد wire call را جدا گزارش کن؛ تنظیم صفر retry سمت client تضمین کنترل retry سمت server نیست.

در benchmark یا سنجش این الگوریتم، همهٔ پاسخ‌های نهایی را با یک full audit مستقل و برابر بررسی کن و false_accept را جدا بشمار. در کار عمومی بدون oracle، معیارهای قابل‌بررسی و پوشش/شکاف بررسی را گزارش بده؛ جواب را صرفاً با اعتماد مدل «اثبات‌شده» ننام.

## گزارش نتیجه

پاسخ نهایی، روش بررسی، provider/model/effort واقعاً درخواست‌شده، تلاش‌ها، usage و محدودیت مادی را کوتاه گزارش کن. input+output را جمع کن؛ cache زیرمجموعهٔ input و reasoning زیرمجموعهٔ output است. usage ناموجود صفر نیست. هزینهٔ API-equivalent، هزینهٔ کیف پول، سهمیهٔ اشتراک و مصرف محلی Laya را جدا نگه دار.

هیچ بهبود عددیِ benchmark Codex قبلی را به مدل‌های GapCode منتقل نکن. آزمون این افزونه، اتصال و سازگاری محدود است. استفاده از اسکیل مجوز ارسال پیام به دیگران، انتشار، تغییر حساب یا انجام کار خارج از درخواست کاربر ایجاد نمی‌کند.
