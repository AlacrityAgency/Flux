# برنامهٔ آزمون مستقل و مقایسه با Flux ۰٫۵٫۱

وضعیت: طراحی آزمون؛ هنوز dataset تازه، prototype یا trial جدید اجرا نشده است. اجرای آزمون موجود امروز ابتدا ۱۲۳ تست و پس از تغییر هم‌زمان دو فایل خارج از این پژوهش، ۱۲۴ تست موفق داشت؛ [manifest اولیه](baseline-manifest.json) و [snapshot نهایی](final-source-manifest.json) جدا حفظ شده‌اند. داده‌های تاریخی JEVS از فایل گزارش خوانده شده‌اند و baseline کیفیت runtime جاری محسوب نمی‌شوند.

## ۱. واحد ارزیابی و baseline

واحد اصلی **task با معیار و snapshot ثابت** است؛ trial یک اجرای همان task است و observation مستقل اضافی محسوب نمی‌شود. rubric، خطاهای بحرانی و labelها پیش از مشاهدهٔ نتایج candidate منجمد شوند.

دو baseline لازم‌اند:

- B0: مسیر کنترل‌شدهٔ HEAD ۰٫۵٫۱، retrieval جاری و انتخاب مدل ثابت/تنظیم امروز؛ baseline اصلیِ تصمیم، کیفیت و منابع.
- Bchat: مسیر گفتگوی حساب‌ها فقط برای مقایسهٔ تجربهٔ کار محصول؛ با B0 مخلوط نشود، زیرا کنترل و ابزارهای آن متفاوت‌اند.

وجود ledger API در B0، دسترسی واقعی حساب API را ثابت نمی‌کند. برای بازوی هزینهٔ مالی، adapter مستقل با usage معتبر نیاز است. در بازوی CLI، فقط سهمیه، usage مشاهده‌شده، تعداد تماس و زمان ثبت شوند؛ نبود مقدار مالی برابر صفر نیست.

## ۲. dataset و جلوگیری از leakage

پیشنهاد آغاز: ۳۰۰ سناریوی تعریف‌شده برای ارزیابی offline، ۶۰ کار end-to-end نمایندهٔ استفادهٔ واقعی و ۳۰ سناریوی خصمانه/lifecycle. این اعداد **برنامه‌اند** و توان آماری تضمین‌شده ندارند. ابتدا ۲۰ سناریوی pilot برای تشخیص مشکلات harness؛ سپس اندازهٔ لازم از واریانس و اثر قابل تشخیص برآورد شود.

خانواده‌ها: یافتن تابع/guard، تغییر چندفایلی، تصمیم معماری، گزارش فارسی و انگلیسی، چندمنبعی، تاریخچهٔ تصمیم متناقض، فایل تغییرکرده/حذف‌شده، criterion بدون شاهد، آزمون تعریف‌شده ولی اجرا نشده، قطعهٔ طولانی و پنجرهٔ کوچک، قطع اجرا و receipt نامعلوم.

taskهای واقعاً نیازمند ویرایش فقط در پروژهٔ sandbox مستقل و در بازوی برابر ابزارها اجرا شوند. HEAD فعلی برای تولید تحلیل فقط‌خواندنی است؛ candidate دارای file write را به عنوان بهبود الگوریتم با B0 فقط‌خواندنی مقایسه نکنیم.

split پیشنهادی بر خانوادهٔ task و revision/project: development، validation، test پنهان. مثال‌های نزدیک و متن مشابه یک خانواده در دو split نیایند. candidate پس از validation منجمد شود. gold، rubric، پاسخ صحیح و متن این گزارش بیرون corpus retrieval باشند. حافظهٔ به‌دست‌آمده از trial یک بازو به بازوی دیگر یا پاسخ همان test منتقل نشود.

دو regime مجزا:

۱. cold/frozen: مخزن دانش اولیه برای همهٔ بازوها یکسان و تغییر ممنوع؛ اثر retrieval/routing سنجیده می‌شود.

۲. longitudinal: taskها به ترتیب زمانی؛ فقط دانش مجاز از taskهای گذشته می‌تواند وارد task بعدی شود. approval یکسان و log promotion حفظ شود. این بازو اثر یادگیری حافظه را می‌سنجد؛ با cold میانگین مشترک نگیرد.

## ۳. ablation؛ اثر هر ماژول و هماهنگی

| بازو | توکن/بسته | تصمیم | حافظه/RAG |
|---|---|---|---|
| B0 | جاری | جاری | جاری |
| T | candidate | جاری | جاری |
| D | جاری | candidate | جاری |
| M | جاری | جاری | candidate |
| TM | candidate | جاری | candidate |
| TD | candidate | candidate | جاری |
| DM | جاری | candidate | candidate |
| TDM | candidate | candidate | candidate با هماهنگی |

نسخهٔ candidate، مدل/adapter، فایل‌های منبع، budget، prompt، tokenizer، hardware و cache regime برای هر بازو ثبت شوند. این جدول نشان می‌دهد آیا بهبود از یک ماژول یا interaction آمده است. درصدهای T/D/M جمع زده نشوند.

retrievalهای lexical جاری، BM25، dense، hybrid، hybrid+rerank نیز جدا مقایسه شوند. برای fusion، RRF و ترکیب خطی؛ برای packing، score-first، gain-per-token و گزینهٔ beam محدود؛ برای compression، none، rule-based و مدل آزمایشی مقایسه شوند. ابتدا cheap offline pruning، سپس فقط candidateهای معتبر به تماس مدل برسند.

## ۴. سنجه‌ها

| محور | سنجهٔ اصلی | نکتهٔ تفسیر |
|---|---|---|
| retrieval | evidence recall، precision، پوشش کامل همهٔ معیارهای لازم، nDCG | recall بالا ممکن است با قطعهٔ اضافی و هزینهٔ بیشتر همراه باشد |
| شاهد | صحت citation، نوع شاهد، نسخه و منشأ | نام فایل آزمون شاهد test_execution نیست |
| خروجی | pass مستقل معیارها، first-pass، rework و خطای بحرانی | «مدل تمام کرد» برابر پذیرش نیست |
| تصمیم | اقدام مناسب، ارجاع درست، escalation بی‌مورد، wasted calls | توقف درست در فقدان اختیار موفقیت کنترل است؛ موفقیت deliverable جدا |
| توکن | local input، reported input/output/reasoning، مجموع تمام تلاش‌ها | تفاوت tokenizer و Context پنهان CLI با missingness گزارش شود |
| اقتصاد | هزینهٔ کل دوره / تعداد task پذیرفته‌شده | شکست، retry، indexing، embedding، compression و review در صورت هزینه‌داربودن داخل numerator |
| زمان | زمان فعال، انتظار انسانی، p50/p95، indexing cold و retrieval warm | زمان retrieval کم به معنی latency نهایی کم نیست |
| حافظه | دقت گزارهٔ استخراج‌شده، duplicate، unresolved conflict، stale selection، سود task بعدی | پذیرش artifact تمام جملاتش را verified نمی‌کند |
| کنترل | budget breach، forbidden dispatch، scope leakage، stale/tombstone resurrection | صفر رخداد در نمونه، تضمین صفر عمومی نیست |
| تجربهٔ انسانی | زمان آماده‌سازی، نظارت، اصلاح و تصمیم | با rubric و owner واقعی در پایلوت جدا سنجیده شود |

اگر accepted_count صفر باشد، نسبت هزینه/توکن به پذیرش undefined است؛ صفر یا صرفه‌جویی کامل ثبت نشود. هنگام مقایسهٔ نرخ قبولی، همهٔ taskهای از پیش تعریف‌شدهٔ واجد ارزیابی در denominator بمانند؛ شکست و timeout حذف نشوند. failure admission و quality failure جدا گزارش شوند.

بازبینی کیفیت: checker قطعی برای معیارهای اجرایی؛ judge blind برای متن باز؛ بازبینی انسانیِ تمام اختلاف‌های مهم و نمونه‌ای از باقی موارد. judge از نام بازو و هزینه بی‌خبر و روی label انسانی کالیبره شود. کیفیت retrieval و answer quality دو گزارش جدا داشته باشند. رویکرد ترکیبی با [راهنمای ارزیابی Anthropic](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents) هم‌راستاست.

## ۵. آزمون ناوردایی و failure injection

موارد اجباری: پروژهٔ دیگر، role فاقد مجوز، global memory غیرمجاز در مدل سازمانی، تزریق دستور داخل سند، tombstone جدید با revision قدیمی verified، proposed edit کنار approved record، لغو دسترسی، تغییر فایل هنگام review، tokenizer unavailable، mandatory prompt بیش از ظرفیت، بستهٔ تهی، wrapper افزوده، هزینهٔ unknown، دو رزرو هم‌زمان، دو receipt متعارض، crash بین ارسال و رسید، retry پنهان adapter و نبود output cap قابل اتکا.

برای هر مورد oracle مشخص باشد: action مجاز/غیرمجاز، محدودهٔ دادهٔ قابل مشاهده، وضعیت رزرو و hash انتظار. اگر provider حقائق لازم برای oracle را گزارش نمی‌کند، آن guarantee با عنوان unsupported/unknown نگهداری شود، نه اینکه fixture ساختگی تأیید سرویس زنده شمرده شود.

## ۶. تحلیل آماری و دروازهٔ نتیجه

مقایسه paired روی taskهای مشترک، با ترتیب اجرای بازوها تصادفی و provider version ثبت‌شده. حداقل سه trial برای کارهای مدلی در pilot؛ تعداد نهایی از واریانس تعیین شود. bootstrap بر task/family، نه هر trial به صورت مستقل. فاصلهٔ اطمینان ۹۵٪ برای اختلاف کیفیت و نسبت هزینه/توکن؛ p95 و tail failure جدا.

شرط پیشنهادی پذیرش candidate:

- تمام ناوردایی‌های قطعی آزموده‌شده پاس شوند و هیچ خطای بحرانی جدید مشاهده نشود؛ failure حل‌نشده مانع rollout است.
- کران پایین اختلاف نرخ قبولی candidate−B0 از **منفی ۲ واحد درصد** پایین‌تر نباشد. اگر نمونه برای این ادعای non-inferiority کافی نیست، نتیجه نامشخص است.
- در بازوی هدف، حداقل **۲۰٪ کاهش توکن مشاهده‌شده به ازای خروجی پذیرفته‌شده** یا **۱۵٪ کاهش هزینهٔ مالی کل به ازای خروجی پذیرفته‌شده**، با فاصلهٔ اطمینان مناسب و numerator کامل؛ انتخاب هدف پیش از آزمون انجام شود.
- tail latency فعال بیش از ۱۰٪ بدتر نشود، مگر trade-off از پیش توافق‌شده‌ای با کیفیت بالاتر داشته باشیم. شاخص جدید پس از دیدن نتیجه به عنوان هدف اصلی انتخاب نشود.

این آستانه‌ها اهداف پیشنهادی هستند؛ نه نتیجهٔ جاری و نه پیش‌بینی مقاله. شرط عددی باید با دامنهٔ کار و قرارداد پایلوت نهایی شود. اطلاعات ناکافی از هزینهٔ CLI نمی‌تواند معیار مالی را پاس کند.

## ۷. مراحل اجرایی بعدی و خروجی قابل بازبینی

۱. ساخت dataset/gold مستقل و fixtureهای baseline؛ خروجی manifest و oracle.

۲. ساخت prototypeهای RAG و packing در همین فضای آزمایشی، بدون import کردن API اصلی برای mutation DB واقعی؛ خروجی بسته و metric offline.

۳. policy تصمیم و capability registry آزمایشی؛ ابتدا replay/shadow که پیشنهاد می‌دهد و dispatch ندارد.

۴. end-to-end فقط در sandbox، با backend و ابزار یکسان و سقف تماس/هزینهٔ مصوب. این سند در این نوبت تماس مدل تازه اجرا نمی‌کند.

۵. گزارش نهایی برای هر بازو: تعداد task/trial، source/candidate hash، missing usage، نمودار کیفیت-هزینه، تأخیر، خطا، و نتیجهٔ go/no-go/نامشخص.

۶. فقط پس از اثبات، طرح اتصال با feature flag، امکان fallback، migration صریح و rollback بررسی شود. تغییر نسخهٔ اصلی یا نصب در این مرحلهٔ پژوهش مجاز تلقی نمی‌شود.

نتیجه‌ای که باید در پایان بتوانیم بگوییم: «روی این taskها و این نسخه، با حفظ این سطح کیفیت، به این مقدار و با این فاصلهٔ اطمینان بهتر شد.» اگر فقط evidence recall بهتر شد، دقیقاً همان ادعا بیان شود؛ عبارت «Flux چند برابر هوشمندتر شد» خروجی معتبر این آزمایش نیست.
