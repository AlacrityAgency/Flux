۴. نقش‌ها و انتخاب اولیهٔ مدل
## ۴. نقش‌ها و انتخاب اولیهٔ مدل

| نقش | وظیفه و خروجی | نامزد اولیه | شرط استفاده |
|---|---|---|---|
| دریافت و دسته‌بندی | استخراج هدف، نوع کار و ابهام‌ها | Gemma ارائه‌شده یا Luna | قواعد ساده ابتدا با کد؛ مدل فقط برای متن مبهم |
| Agent اصلی | قرارداد کار، وابستگی‌ها، طرح و جمع‌بندی | Terra؛ ارتقا به Sol | برای تصمیم پیچیده؛ کار تکراری از قالب تأییدشده استفاده کند |
| مجری معمولی | تغییر محدود کد، پیش‌نویس تست یا سند | Luna؛ Qwen به‌عنوان نامزد مقایسه | فقط پس از ارزیابی روی کار واقعی شرکت |
| مجری کار دشوار | اصلاح چندفایلی در محدودهٔ مشخص | Terra | پس از تشخیص پیچیدگی یا یک شکست قابل تشخیص |
| بازبین کد | بررسی diff، شواهد و معیارهای پذیرش | Sol | مکالمهٔ مستقل از مجری؛ بدون اختیار تغییر معیارها |
| خلاصه‌ساز | گزارش کوتاه همراه پیوند به شواهد | Luna یا قالب نرم‌افزاری | بدون فراخوانی اضافی اگر دادهٔ ساخت‌یافته کافی باشد |
| موتور هماهنگی | صف، بودجه، وضعیت، دسترسی و ثبت رخداد | کد معمولی | مدل نیست |

این جدول ادعای برتری کیفی مدل‌ها نیست؛ یک چیدمان قابل آزمایش با قیمت‌های داده‌شده است. در پایلوت هم‌زمان همهٔ مدل‌های فهرست را فعال نمی‌کنیم. مدل‌های پرهزینه فعلاً نامزد پیش‌فرض نیستند. قیمت پایین‌تر بدون نرخ قبولی مناسب، صرفه‌جویی ایجاد نمی‌کند.

قبل از فعال‌کردن هر نامزد، adapter باید شناسهٔ واقعی API، ابزارخوانی، قالب JSON، محدودیت ورودی/خروجی، تعرفهٔ توکن استدلال، گزارش usage و خطاها را آزمایش و ثبت کند. مدل ناسازگار از مسیر نیازمند آن قابلیت حذف می‌شود. دسترسی حساب Codex به یک نام مدل، اثبات دسترسی API شرکت به همان نام نیست.

بازبینی مستقل با یک مدل دیگر نیز تضمین درستی نیست. تست اجرایی، بررسی نتیجه و قضاوت انسانی مکمل آن هستند؛ این ترکیب با دسته‌بندی ارزیابی‌های کدی، مدلی و انسانی در [راهنمای ارزیابی Agentها](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents) هم‌راستا است.

[README.md#استفاده]
## استفاده

1. در «اتصال حساب‌ها» آماده بودن Claude Code و Codex را ببین.
2. پوشهٔ پروژه، دستیار و مدل را انتخاب کن. مدل خالی از تنظیم پیش‌فرض همان CLI استفاده می‌کند.
3. دسترسی «خواندن، ویرایش و اجرا» برای انجام واقعی کار است. «فقط خواندن» برای بررسی فایل‌هاست.
4. پیام را بفرست؛ پاسخ، فرمان‌ها و تغییر فایل‌ها در گفتگو و «فعالیت ابزارها» دیده می‌شوند.
5. پیام بعدی همان نشست را ادامه می‌دهد. برای عوض کردن دستیار، مدل یا پوشه، گفتگوی تازه بساز.

دکمهٔ ارسال هنگام اجرا به «توقف اجرا» تبدیل می‌شود. Enter ارسال و Shift+Enter خط جدید است؛ Ctrl+K گفتگوی تازه می‌سازد. پاسخ را می‌توان کپی یا به Markdown صادر کرد. حافظهٔ منتخب از یادداشت‌های محلی قبلی بازیابی می‌شود.

## DEMO-03 — موتور اجرا و تاریخچهٔ پایدار

خروجی: اجرای واقعی گردش کار با provider جعلی و حفظ state پس از بستن برنامه.

- [ ] ساخت SQLite و migration برای runs، subtasks، calls، artifacts، checks، decisions و events.
- [ ] پیاده‌سازی state machine و صف وابستگی با حداکثر دو Agent هم‌زمان برای کل برنامه.
- [ ] اتصال worker و event queue به UI؛ به‌روزرسانی مراحل بدون مسدودکردن پنجره.
- [ ] ثبت اتمی state و event؛ جلوگیری از اجرای دوباره با دوبار کلیک/idempotency.
- [ ] اعمال سقف ۲۰ فراخوانی، دو ارسال Head، سه تلاش زیرکار، یک ارتقای مجاز و ۲۰ دقیقهٔ فعال؛ حفظ شمارنده‌ها.
- [ ] لغو، checkpoint، بازیابی و قفل تک‌نمونهٔ برنامه؛ تماس نامعلوم پس از crash خودکار تکرار نشود.
- [ ] ذخیرهٔ خروجی با ref/hash و نمایش تاریخچه و علت توقف در UI.

فایل‌های پیشنهادی: `engine/`، `storage/`، `artifacts.py`، `ui/run_view.*`، `ui/history_view.*`.

معیار پایان: جریان fake از ثبت تا بررسی برسد؛ دوبار شروع یک run بسازد؛ هم‌زمانی از دو بیشتر نشود؛ پس از restart داده و شمارنده باقی بمانند؛ پاسخ دیررس وضعیت لغوشده را برنگرداند.

## DEMO-02 — قراردادها و پنج Agent آزمایشی

خروجی: پنج نقش با ورودی/خروجی ساخت‌یافته و پاسخ‌های قابل تکرار.

- [ ] تعریف Task، Plan، AgentEnvelope، Review و Result؛ ثابت‌کردن معیارها با hash قرارداد.
- [ ] تعریف Head، Planning، Technical، Execution و Verification با prompt نسخه‌دار و سقف خروجی جدا.
- [ ] تعریف Provider interface و Fake Provider با سناریوهای موفق، JSON خراب، timeout و usage ناموجود.
- [ ] اعتبارسنجی ورودی و سیاست فضای کاری: هدف/معیار/بودجه، دادهٔ secret، فایل و ابزار مجاز.
- [ ] اعتبارسنجی routing: حداکثر پنج زیرکار، شناسهٔ یکتا، dependency موجود و گراف بدون دور.
- [ ] آماده‌کردن دو plan جعلی: سند ساده با سه نقش و پیشنهاد فنی با پنج نقش.

فایل‌های پیشنهادی: `contracts.py`، `agents/`، `providers/base.py`، `providers/fake.py`، `policy.py`، `examples/`.

معیار پایان: ورودی نامعتبر با صفر تماس متوقف شود؛ plan نامعتبر اجرا نشود؛ هر نقش schema مشخص داشته باشد؛ مدل نتواند معیارها را تغییر دهد. تست پیش‌فرض اجازهٔ شبکه ندارد.

## DEMO-04 — مدیریت توکن و هزینه

خروجی: کنترل بودجه قبل از هر تماس و نمایش روشن مصرف.

## ۹. معیار تحویل

سه مثال قابل تکرار: سند ساده، برنامه‌ریزی و تغییر کوچک کد در runner. جریان موفق و شکست با Fake Provider اجرا شود؛ ۱۲ تست الزامی پیوست و تست‌های رقابت بودجه، cancel/restart، مسیر نامجاز و retry هزینهٔ نامعلوم پاس شوند. تست عادی هیچ شبکه‌ای باز نکند. نصب پاک، راه‌اندازی مجدد و بازیابی state نشان داده شوند. adapter واقعی فقط پس از ثبت قابلیت‌ها و smoke test محدود فعال شود.

پیش‌نیازهای باقی‌مانده برای اجرای زنده: سیاست واقعی دامنهٔ شرکت و پروژهٔ نمونه، پنج ID و تعرفهٔ قابل اثبات، کلید معتبر در محیط، runtime جداسازی و Taskهای نمونه با معیار روشن. این‌ها مانع ساخت موتور و تست جعلی نیستند.

برنامهٔ اجرایی در [بک‌لاگ MVP](mvp-tasks.fa.md) است.

## معماری کوچک‌تر برای یک کاربر

Python + PySide6 برای پنجره و موتور، SQLite برای حافظه/وضعیت/دفتر مصرف. رابط با worker داخلی و event queue کار می‌کند تا هنگام تماس مدل مسدود نشود. سرویس HTTP و هفت endpoint پیوست برای این دمو لازم نیستند؛ API داخلی به شکل interface پایتونی جدا می‌ماند تا بعداً wrapper HTTP اضافه شود. موتور یک instance فعال برای پوشهٔ داده دارد.

داده زیر `%LOCALAPPDATA%\FluxDemo\` مستقل از فایل برنامه ذخیره می‌شود. برنامه با shortcut و runtime همراه اجرا شود؛ نسخهٔ portable کافی است و نصاب حرفه‌ای، updater و سرویس پس‌زمینه نیاز نیست. با بستن برنامه، اجرای تازه متوقف و checkpoint ثبت می‌شود؛ بعد از بازکردن، کار نامعلوم بدون بررسی دوباره ارسال نمی‌شود. یک export/backup سادهٔ سازگار SQLite و فایل‌ها برای جلوگیری از وابستگی به یک پوشه کافی است.

## ۱۴. معیار آماده‌بودن برای اجرا

- قرارداد کار، وضعیت‌ها، مالکیت و گراف بدون دور در حالت mock قابل نمایش باشند.
- موتور درخواست ابزار خارج از مجوز را مستقل از متن مدل رد کند.
- سقف بودجه در دو اجرای هم‌زمان، timeout و restart حفظ شود.
- شکست تست مانع ACCEPT_CANDIDATE شود و نبود شواهد به‌اشتباه قبولی نگیرد.
- Agent پس از سه تلاش یا تکرار بدون پیشرفت متوقف شود.
- یکپارچگی خروجی روی revision مشخص بررسی و پذیرش به همان خروجی متصل شود.
- هیچ مدل تأییدنشده از نظر قابلیت یا تعرفه به حساب واقعی وصل نشود.
- سنجه‌ها شکست، هزینهٔ retry و زمان انسان را حذف نکنند.

چک‌های فوق برای پیاده‌سازی آینده‌اند. این تحویل فقط طرح، تنظیمات پیشنهادی و محاسبهٔ آفلاین بودجه را فراهم می‌کند.
