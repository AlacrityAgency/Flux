امکانات بخش پروژه‌ها:
### امکانات بخش پروژه‌ها:
1. **تب «پروژه‌ها و پوشه‌ها» در نوار کناری**: با کلیک روی این بخش، نمای مدیریت پروژه‌ها باز می‌شود.
2. **نوار تب‌های باز (Tabs Bar)**: در بالای صفحه پروژه‌ها، تب «همهٔ پروژه‌ها» به همراه تب‌های اختصاصی هر پروژه که باز می‌کنید قرار دارد تا بتوانید به راحتی بین پروژه‌های مختلف جابه‌جا شوید.
3. **تعریف پروژه با مسیر پوشه (Path)**:
   - نام پروژه (مثلاً: «سایت شرکت» یا «ربات معاملاتی»)
   - مسیر پوشه روی سیستم (مانند `D:\project\my-app`) با **اعتبارسنجی زنده** (بررسی وجود پوشه، شمارش فایل‌ها و پوشه‌ها)
   - توضیحات و اهداف کلی پروژه
   - معیارهای پیش‌فرض پذیرش تسک‌های پروژه
   - سقف بودجهٔ پیش‌فرض
4. **بازرس ساختار فایل‌های پوشه (Folder Inspector)**:
   - نمایش وضعیت اتصال پوشه روی سیستم
   - دکمهٔ «کپی مسیر» و دکمهٔ **«باز کردن در Explorer»** برای باز کردن پوشه مستقیماً در Windows Explorer
   - پنل کشویی لیست فایل‌های داخل پوشه
5. **مدیریت تسک‌های پروژه**:
   - افزودن تسک جدید با عنوان، هدف، معیارهای پذیرش خط به خط، اولویت (`P0` تا `P3`) و سقف بودجه.
   - دکمهٔ **«اجرای تسک»**: تسک را همراه با زمینهٔ فایل‌های موجود در پوشه به موتور ۵ Agent ارسال می‌کند.
   - دکمهٔ **«گفت‌وگو»**: باز کردن سریع اجرای تسک در صفحهٔ چت برای مشاهدهٔ مراحل ۵ Agent و پذیرش خروجی.
6. **اتصال پروژه به گفت‌وگوی اصلی**:
   - در نوار پایین نوشتن پیام (Composer)، دکمهٔ انتخاب پروژه اضافه شده تا هر پیامی که می‌نویسید بتواند مستقیماً به پوشهٔ یک پروژه متصل شود.

## ۷. ابزار، context و شواهد

Artifact store محلی با ref نسبی داخلی، project_id، revision، hash و data_class داشته باشیم. ref به‌تنهایی مجوز خواندن نیست؛ مجوز در هر خواندن دوباره بررسی شود. context فقط قرارداد ثابت، خلاصهٔ نسخه‌دار و منابع مرتبط را می‌گیرد. Review diff و شواهد لازم را دریافت می‌کند؛ تاریخچهٔ گفتگوهای مجری ارسال نمی‌شود. hash درخواست read-only شامل پروژه، قرارداد، مدل، prompt/schema/policy version، پارامترها و hash ورودی‌هاست؛ cache هزینهٔ قبلی را دوباره حساب نمی‌کند و میان پروژه‌ها مشترک نیست.

شروع ابزارها با read مجاز، نوشتن artifact داخلی و تولید patch محدود است. برای اجرای واقعی تست/کد، runner جدا و محدود لازم است: فضای موقت، inputهای مجاز read-only، خروجی جدا، network خاموش، بدون کلید محیط، محدودیت CPU/RAM/process/time و بدون mount میزبان یا Docker socket. allowlist دستور به‌تنهایی sandbox نیست؛ تست هم می‌تواند کد دلخواه اجرا کند. اگر runtime جداسازی آماده نیست، تولید diff مجاز است ولی اجرای تست not_run و نامزد قبولی فنی مسدود می‌ماند.

حدود مسیر با canonical path و کنترل junction/symlink و traversal در Windows اعمال شوند. API مدل اجازهٔ shell عمومی ندارد؛ فراخوانی ابزار ساخت‌یافته و allowlist آرگومان دارد. حتی allowed_tools نمی‌تواند ممنوعیت deploy، merge، حذف فایل و پیام خارجی را دور بزند. محتوای فایل و خروجی مدل هرگز policy را تغییر نمی‌دهد. audit شامل metadata، hash و دلایل کوتاه است؛ secret و header احراز هویت و متن حساس کامل در log ذخیره نشود. طبقه‌بندی دستی به‌تنهایی کافی نیست؛ منابع ورودی نیز پیش از prompt از نظر secret بررسی شوند.

## حافظه و دقت در حد دمو

SQLite محلی، فایل‌های متنی منتخب و جست‌وجوی متنی فارسی کافی‌اند. هر نکتهٔ حافظه منبع، نسخه و وضعیت پیشنهادی/تأییدشده/منسوخ دارد. فقط بخش مرتبط در سقف context بازیابی می‌شود؛ کل تاریخچه با هر درخواست ارسال نمی‌شود. نتیجهٔ خود Agent بدون تأیید کاربر به حقیقت دائمی حافظه تبدیل نمی‌شود. ویرایش یا حذف، نمایه و cache وابسته را هم تازه می‌کند.

دقت با معیار روشن، ارجاع به منبع، بررسی مستقل و علامت‌زدن موارد نامعلوم کنترل می‌شود. خروجی کد در این دمو «پیشنهاد کد/diff بررسی‌شده» است. اجرای خودکار کد و shell، دستکاری مستقیم مخزن و runner ایزوله از دمو خارج‌اند؛ تست اجرا نشده با برچسب not_run نشان داده می‌شود. اگر معیار Task نیازمند اجرای تست باشد، نتیجه بدون آن ACCEPT_CANDIDATE نمی‌شود. این محدودیت دامنه را کم می‌کند و نباید در UI پنهان شود.
