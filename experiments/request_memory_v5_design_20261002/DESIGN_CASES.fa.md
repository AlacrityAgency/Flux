# موارد پذیرش طراحی v5

وضعیت: **خروجی‌های موردانتظار طراحی؛ هیچ‌کدام نتیجهٔ اجرای v5 نیستند.** این مثال‌ها پیش از کدنویسی برای بررسی قرارداد تعیین شده‌اند. الگوریتم کامل در `ALGORITHM.fa.md` است.

| ورودی و شرایط | رفتار موردانتظار | تماس تولید |
|---|---|---:|
| سؤال owner سرویس alpha01؛ شاهد alpha01=team03 و beta02=team09؛ مدل team09 می‌گوید | انتساب به entity اشتباه رد شود؛ اگر شاهد درست حاضر است، یک اصلاح مجاز | حداکثر ۲ |
| شاهد typed مقدار limit_ms=250؛ مدل عدد 25 می‌گوید | برابری زیررشته‌ای ممنوع؛ contradicted و حداکثر یک اصلاح | حداکثر ۲ |
| سؤال مقدار مجاز Contract.human_owner؛ قرارداد Literal برابر local-user و fixture برابر Danial است | منبع contract و مجموعهٔ literal مبنا باشد؛ fixture پوشش این نیاز نیست | عادی ۱ |
| سؤال «مالک انسانی پروژه چه کسی است؟» بدون نام کلاس و با alias عمومی | project_grounded یا uncertain با probe؛ نبود anchor باعث بستهٔ خالیِ self_contained نشود | ۰ یا ۱؛ تابع روشن شدن نیاز |
| عبارت خودبسنده 2+2 و پاسخ 4؛ checker مستقل همین عبارت را پشتیبانی می‌کند | بستهٔ خالی مجاز؛ verified با proof محاسباتی، نه proof شاهد RAG | ۱ |
| درخواست افزودن رفتار به تابع موجود repository | task_kind=code و memory_need=project_grounded؛ سورس مرتبط و اجرای تست عمومی مجاز | حداکثر ۲ |
| تمام رکوردهای پروژه deleted/stale یا snapshot خالی | no_evidence/missing؛ ایندکس صفر واحد معتبر و بدون خطای vocabulary | ۰ اگر شاهد ضروری است |
| بودجه حتی header اجباری را جا نمی‌دهد | budget_infeasible؛ هیچ evidence pack موفق و هیچ تماس مدل | ۰ |
| دو class هم‌نام با مقادیر متفاوت و context ناکافی | ambiguous؛ انتخاب اولین نتیجه یا میانگین‌گیری score ممنوع | ۰ تا رفع ابهام |
| مدل required field را حذف می‌کند یا همه را null می‌دهد | partial/abstained؛ verified کامل نیست | حداکثر ۲؛ طبق امکان اصلاح |
| پاسخ آزاد با citation معتبر ولی بدون checker معنایی | citation و span قابل‌بررسی، semantic unverified حفظ شود | عادی ۱ |
| اصلاح دوم همچنان غلط است | توقف؛ تماس سوم ممنوع و failure/partial حفظ شود | دقیقاً حداکثر ۲ |
| تغییر revision منبع پس از ساخت pack و پیش از پذیرش خروجی | receipt قبلی stale شود؛ پذیرش خودکار انجام نشود | تماس خودکار اضافی ندارد |
| note تولیدی مدل حتی با citation و پاسخ پذیرفته‌شده | پیشنهاد حافظه، نه حقیقت eligible؛ ارتقای جداگانه مطابق قرارداد Flux | ۰ برای نوشتن پیشنهاد |

در تست اجرایی باید تماس‌ها با ledger شمارش شوند، نه با تعداد توابع فراخوانی‌شده. معیار «verified» در هر مورد فقط به proof_kind مشخص و نیازهای required همان درخواست مربوط است.
