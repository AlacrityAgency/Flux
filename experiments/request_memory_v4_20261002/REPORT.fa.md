# گزارش v4: حافظهٔ درخواست، یک‌گذره و بدون مخزن یک‌میلیونیِ هر درخواست

تاریخ: ۲ اکتبر ۲۰۲۶. همهٔ آزمایش‌ها offline اجرا شدند و **هیچ فراخوانی مدلی انجام نشد**. Flux اصلی و پوشهٔ v3 تغییری نکردند.

## چه چیزی عوض شد

| v3 | v4 |
|---|---|
| ساخت مخزن ۱M برای هر درخواست (حدود ۱٫۹ ثانیه) | حذف شد؛ ایندکس یک بار برای هر snapshot ساخته می‌شود |
| شمارش دوبارهٔ توکن کل payload در هر حلقه | توکنِ هر واحد یک بار موقع ایندکس شمرده می‌شود؛ در هر درخواست فقط یک شمارش دقیق انجام می‌شود |
| optimizer با برنامهٔ ثابت حذف و یک rollback نمایشی | حذف شد؛ انتخاب یک‌گذره زیر بودجه |
| `svc\d{5}` و نام فیلدها در کد نوشته شده بود | قاعدهٔ مخصوص داده وجود ندارد (یک تست این را چک می‌کند) |
| need noteها با فراخوانی LLM (۱۸ ثانیه) | RequestSpec قطعی بدون مدل |
| — | شکستن شناسه به زیرواژه (`held_unknown` → `held` و `unknown`) |
| — | محدودهٔ `def`/`class` نام‌برده‌شده و رتبهٔ بالاتر برای واحدی که چند anchor به آن می‌رسند |
| — | hop رابطه‌ای عمومی (نامی که در یک واحد آمده و خانه‌اش در واحد دیگری است) |
| — | router: درخواست خودبسنده (ریاضی یا کد) بستهٔ خالی می‌گیرد |
| — | verifier قطعی بعد از تولید و حداکثر یک repair |

## روش آزمون

- **dev** (برای طراحی و تنظیم): corpus مصنوعی با seed 6417 (۱۳۶ تسک) و ۱۲ تسک واقعی روی snapshot منجمد Flux.
- **انجماد**: ۲۸۸ پیکربندی روی dev آزموده شد و یکی با قاعدهٔ از پیش تعیین‌شده انتخاب شد: lexical، `per_criterion=3`، `scope_k=2`، `neighbors=1`، `fill=0`، `beta=0.25`. hash کد در `frozen-plan.json` ثبت شد و holdout اگر کد عوض شده باشد اجرا نمی‌شود.
- **holdout** (فقط یک بار اجرا شد، ۱۵۶ تسک):
  - corpus مصنوعی تازه با seed 20261002 (۱۳۶ تسک)؛
  - ۸ تسک منجمد خود v3؛
  - ۱۲ تسک واقعی تازه (`holdout_tasks.py`) که hash آن‌ها پیش از نوشتن v4 ثبت شده بود.
- **سنجه‌ها**:
  - کامل‌بودن شواهد: همهٔ رشته‌های طلایی در بسته باشند؛
  - توکن بسته؛
  - توکنِ «نویز»: واحدهایی که هیچ رشتهٔ طلایی ندارند؛
  - زمان مسیر درخواست. embedding پرسش در v3 هر بار واقعاً محاسبه شد و از cache خوانده نشد.

## نتیجهٔ holdout

| | v3 fixed-1M | v3 adaptive | **v4** |
|---|---|---|---|
| تسک با شواهد کامل | ۱۵۵/۱۵۶ (۹۹٫۴٪) | ۱۳۹/۱۵۶ (۸۹٫۱٪) | **۱۵۶/۱۵۶ (۱۰۰٪)** |
| زمان میانه | ۱۹۱۰ ms | ۱۲۳ ms | **۱٫۲ ms** |
| زمان p95 | ۱۹۴۰ ms | ۱۸۶ ms | **۲٫۰ ms** |
| میانگین توکن بسته | ۲۵۳۴ | ۱۳۷۱ | **۳۲۴** |
| میانگین توکن نویز | ۲۳۹۳ | ۱۲۰۲ | **۲۱۱** |
| تخطی از بودجه یا خطا | ۰ | ۰ | ۰ |

v4 نسبت به v3 fixed-1M:
- **زمان مسیر درخواست ۹۹٫۹۴٪ کمتر** (هدف ۹۵٪ برآورده شد)؛
- **توکن بسته ۸۷٪ کمتر** و **نویز ۹۱٪ کمتر** (هدف ۹۵٪ برای نویز برآورده نشد)؛
- تسک‌های ناقص از ۱ به ۰ رسید. چون v3 fixed فقط یک خطا داشت (F01)، این اختلاف از نظر آماری معنادار نیست (بازهٔ اطمینان ۹۵٪ اختلاف بین ۰ و ۱٫۹ واحد درصد).

v4 نسبت به v3 adaptive: تسک‌های ناقص از ۱۷ به ۰ رسید (همه two-hop بودند و F01). اختلاف کامل‌بودن ۱۰٫۹ واحد درصد است، با بازهٔ اطمینان ۹۵٪ بین ۶٫۴ و ۱۶٫۰.

به تفکیک مجموعه:

| مجموعه | کامل‌بودن (v3 fixed / v4) | توکن بسته (v3 fixed / v4) |
|---|---|---|
| مصنوعی تازه (۱۳۶) | ۱۰۰٪ / ۱۰۰٪ | ۲۴۸۵ / ۱۹۹ (−۹۲٪) |
| تسک‌های منجمد v3، مصنوعی (۶) | ۱۰۰٪ / ۱۰۰٪ | ۲۵۷۴ / ۲۴۰ (−۹۱٪) |
| تسک‌های منجمد v3، واقعی (۲) | ۵۰٪ / ۱۰۰٪ | ۲۹۹۵ / ۱۹۷۱ (−۳۴٪) |
| واقعی تازه (۱۲) | ۱۰۰٪ / ۱۰۰٪ | ۲۹۸۷ / ۱۵۱۴ (−۴۹٪) |

router روی هر ۲۰ تسک برنامهٔ v3 درست تصمیم گرفت: برای ۸ تسک بازیابی کرد و برای ۱۲ تسک استدلالی و کد بسته را خالی گذاشت.

## چیزهایی که باید صادقانه گفت

1. **کیفیت پاسخ مدل اندازه‌گیری نشده است.** «کامل‌بودن شواهد» شاخص ورودی مدل است، نه درستی جواب. ادعای «۹۵٪ خروجی بهتر» فقط با اجرای واقعی luna روی همین بسته‌ها قابل سنجش است.
2. **روی کد واقعی هنوز نویز زیاد است.** حدود ۱۳۵۰ توکن از ۱۵۱۴ توکن بسته رشتهٔ طلایی ندارد. بخشی از آن context مفید است ولی این سنجه آن را نویز حساب می‌کند.
3. **ساخت ایندکس v4 کندتر از v3 است**: ۴٫۲ ثانیه در برابر ۰٫۳ ثانیه برای ۱۱هزار واحد. این کار برای هر snapshot فقط یک بار انجام می‌شود. v3 در عوض برای هر درخواست ۱٫۹ ثانیه خرج می‌کند، پس از درخواست سوم به بعد v4 جلو می‌افتد.
4. **embedding روی dev کمکی نکرد** و با قاعدهٔ انتخاب کنار رفت. پرسش‌های بدون شناسه یا مترادف‌محور در این مجموعه کم بود؛ ممکن است آن‌جا لازم شود.
5. تسک‌های واقعی holdout را خودم نوشتم. ۱۲ تسک کم است و نوع پرسش‌ها به dev شبیه است.

## سرعت کل خروجی (تخمین، نه اندازه‌گیری)

یک فراخوانی luna از طریق Codex CLI حتی برای پاسخ ۷ توکنی ۹٫۹ ثانیه طول کشید و ۱۶٬۸۲۳ توکن ورودی پنهان داشت. طرح v3 برای هر درخواست حدود ۵ تا ۷ فراخوانی پشت‌سرهم دارد؛ v4 یک فراخوانی دارد و دومی فقط اگر verifier رد کند. پس زمان کل حدود ۸۰ تا ۸۵٪ کم می‌شود. **رسیدن به ۹۵٪ در زمان کل با CLI ممکن نیست**، چون همان یک فراخوانی کف زمان است. اهرم بعدی API مستقیم به‌جای CLI است.
